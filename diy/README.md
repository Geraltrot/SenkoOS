# SenkoPhone 1.0 — ретранслятор MeshCore на самодельной плате (ESP32 WROOM-32 + E22-900M30S)

Название платы задаётся в `variants/diy_e22_wroom32/platformio.ini` (`DIY_BOARD_NAME`); технический идентификатор в тегах и сборках — `e22wroom` / `DIY_E22_WROOM32_*`.

Это репозиторий upstream [MeshCore](https://github.com/meshcore-dev/MeshCore). Наши изменения лежат отдельными коммитами поверх релиза `repeater-v1.18.0`.

## Железо (сверено с нетлистом платы, проект `DIY_Meshtastic`)

| Узел | Что стоит | Пины ESP32 |
|---|---|---|
| MCU | ESP32 DevKit V1, 30 pin (WROOM-32, 4 МБ flash, без PSRAM) | — |
| Радио | EBYTE E22-900M30S (SX1262 + PA 1 Вт), питание +5 В | NSS 18, SCK 5, MOSI 27, MISO 19, NRST 23, BUSY 32, DIO1 33, TXEN 13, RXEN 14 |
| Дисплей | OLED 128×128 SH1107, I2C 0x3C | SDA 21, SCL 22 |
| Кнопка | BTN, внешняя подтяжка R1, активный низкий | GPIO39 |
| Светодиод TX | светодиод на DevKit | GPIO2 |
| Питание | 2×18650, DC-DC; АЦП батареи нет | — |

DIO2 у E22 на плате не подключён. Антенным переключателем управляют TXEN/RXEN с GPIO, поэтому `SX126X_DIO2_AS_RF_SWITCH` не задаётся.
Мощность ограничена значением 22 dBm на SX1262: на выходе E22 это примерно 30 dBm. Ставить больше нельзя.

Радиопрофиль по умолчанию: 868.918 МГц, BW 62.5, SF9, CR7, 22 dBm. Он применяется только при первом запуске. Дальше параметры хранятся в настройках устройства.

## Сборка

Нужны Python 3 и PlatformIO (`pip install platformio`).

```bash
pio run -e DIY_E22_WROOM32_repeater
```

Результат: `.pio/build/DIY_E22_WROOM32_repeater/firmware.bin`.

Свои пути к PlatformIO и тулчейну можно задать в `platformio.local.ini` рядом с `platformio.ini` (файл не попадает в git), например `[platformio]` / `core_dir = …`. Если сборка падает с ошибкой `Cannot create temporary file` или `Permission denied` на файлах `.d`, укажите для TEMP/TMP и `PLATFORMIO_BUILD_DIR` папку на другом диске.

## Прошивка

Пошагово для готовых файлов из выпусков (первая прошивка чистой платы, первая настройка, обновление по Wi-Fi и USB, восстановление) — `diy/FLASHING.md`.

Обновление поверх уже прошитого устройства. Пишется только приложение, ключи и настройки сохраняются:

```bash
pio run -e DIY_E22_WROOM32_repeater -t upload --upload-port COM3
```

Если плата не входит в режим загрузки: зажать BOOT, нажать и отпустить RESET (EN), отпустить BOOT.

После первой прошивки задайте в CLI по USB (115200) свой пароль администратора: `password <новый>`. Сам пароль в репозиторий не записывается.

### Переход с другой прошивки (MeshCoreTel, MeshOS и т. п.)

- **Слот загрузки.** Если старую прошивку ставили по OTA, загрузчик может стартовать с `app1`, а не с `app0`, куда пишет `upload`. После записи сотрите раздел otadata командой `esptool.py erase_region 0xE000 0x2000`. Ключи и настройки этим не затрагиваются.
- **Настройки.** Форки хранят файл настроек со своим порядком полей. Имя и частота могут прочитаться правильно, а остальные поля нет. Проверьте и при необходимости задайте заново все значения:

  | Команда | Значение |
  |---|---|
  | `get flood.max` / `flood.max.unscoped` | 64 |
  | `get flood.max.advert` | 8 |
  | `get advert.interval` | 60 |
  | `get radio.rxgain` | on |
  | `get repeat` | on |
  | `get af` | 1.0 |

  Например, `flood.max.advert 0` полностью запрещает пересылку объявлений.
- **Плата на CH340.** Автосброс в режим загрузки на этой плате не работает. Зажмите BOOT, нажмите и отпустите RESET, отпустите BOOT. Терминал открывайте с отпущенными DTR/RTS, иначе ESP32 останется в сбросе.

## Wi-Fi и веб-панель

Wi-Fi включается в CLI по USB. Пароль хранится в NVS платы, а не в коде:

```
wifi ssid <имя сети>
wifi pwd <пароль>       (после ввода плата сама подключается)
wifi            (статус и IP)
wifi connect    (переподключиться)
wifi off        (забыть сеть и выключить Wi-Fi)
```

Команды `wifi …` работают только по USB и из веб-консоли. Через LoRa они недоступны.

Панель открывается по адресу `http://<IP репитера>/`, вход по паролю администратора репитера. Работает по HTTP, поэтому использовать её можно только в домашней сети и не пробрасывать в интернет.

| Вкладка | Что показывает |
|---|---|
| Обзор | аптайм и память, радио, шум с графиком за 4 мин, последний пакет, эфир за сутки, Wi-Fi, часы, пересылка, кнопки advert; графики за час |
| Пакеты | эфирное время с загрузки, за 5 мин и за 24 ч; счётчики по типам; графики за сутки; живой журнал с паузой |
| Каналы | хэши каналов со счётчиками, блокировка канала или #хэштега, публичный канал вкл/выкл; входные репитеры, блокировка репитера или маршрута A>B |
| Сеть | дерево путей в репитер; соседи с именами и SNR в обе стороны, сканирование; трассировка туда и обратно |
| Настройки | все параметры узла, радио, пересылки и таймингов, Wi-Fi, регионы (каждое поле — команда CLI) |
| Консоль | любая команда CLI, как по USB |
| Обслуживание | отдельный пароль веб-входа, загрузка `firmware.bin` по Wi-Fi (OTA), перезагрузка |

Как устроено:
- `DiyMesh` (подкласс `MyMesh`) собирает данные через виртуальные хуки upstream: `logRx`/`logTx`, `onAdvertRecv`, `onControlDataRecv`, `onTraceRecv`. Блокировки работают через `allowPacketForward`: сначала решает upstream, наш фильтр только добавляет запреты для сообщений каналов. Списки блокировок хранятся в NVS.
- История лежит на устройстве в RAM: журнал на 150 пакетов, час по минутам, сутки по 10 минут, шум за 4 минуты. После перезагрузки она обнуляется. Всего около 20 КБ.
- Часы синхронизируются по NTP через Wi-Fi и переводятся только вперёд.
- На ESP32 без PSRAM таблицы ограничены: 64 узла, 320 вершин графа (редкие пути вытесняются), 32 канала, 48 входных репитеров, по 16 блокировок каждого вида.

Обновление по Wi-Fi: вкладка «Обслуживание», файл `<тег>.bin` из релиза. Панель выдаёт одноразовый токен (5 минут, одна загрузка), а файл принимает отдельная задача на порту 8081. Основной цикл при этом продолжает пересылать пакеты. Не сбрасывайте плату до сообщения «Готово», иначе обновление не применится, а на плате останется старая прошивка.

Карта (вкладка «Карта») показывает узлы, приславшие координаты в объявлениях. Leaflet и подложку OpenStreetMap загружает браузер из интернета, плате доступ в интернет не нужен.

Экран: имя, радио, IP панели или состояние Wi-Fi, RX/TX, шум, аптайм, версия. Гаснет через 30 с, кнопка будит. Сам включается, когда Wi-Fi получает адрес.

Версия: команда `diy` в CLI. Схема тега: `v<наша версия>-<плата>-mc<версия MeshCore>-<ГГГГММДД>`, например `v1.0.0-e22wroom-mc1.18.0-20261112`. CI подставляет тег в прошивку и называет файлы релиза `<тег>.bin` и `<тег>-merged.bin`.

Чего нет по сравнению с MeshOS (нет сервиса или железа): облачный observer, онлайн-обновление с их сайта, AirLink и Bluetooth, Ethernet, напряжение батареи, «повреждённые копии», coding rate соседей.

Устройство отдаёт только JSON, интерфейс рисует браузер. Страница `diy/firmware/web/index.html` при сборке сжимается gzip и встраивается в прошивку скриптом `diy/scripts/embed_web.py`. Если открыть этот файл с диска, страница покажет демо-данные: так удобно править дизайн без платы.

## MQTT → Home Assistant

Ретранслятор отправляет свои данные в брокер MQTT (Mosquitto в Home Assistant) и сам создаёт устройство с датчиками через MQTT discovery — в HA ничего писать не нужно.

Включение (по USB, в «Консоли» или «Настройки → MQTT → Home Assistant»):

```
mqtt host 192.168.1.x
mqtt user <пользователь брокера>
mqtt pwd <пароль>
mqtt on
mqtt
```

`mqtt` без параметров показывает состояние (`connected` — всё работает). Прочее: `mqtt port <n>` (1883), `mqtt interval <с>` (30–3600, по умолчанию 60), `mqtt off`, `mqtt discovery` (переслать описания датчиков). Пароль хранится в NVS платы и нигде не выводится. Команды `mqtt …` работают только по USB и из веб-консоли.

Темы: `senkophone/<id>/status` (`online`/`offline`, LWT), `senkophone/<id>/state` (JSON), `homeassistant/sensor/senkophone_<id>_<датчик>/config`. `<id>` — первые 4 байта ключа узла.

Датчики: принято/передано пакетов (всего и за минуту), шум эфира, SNR и RSSI последнего пакета, эфир TX/RX за 24 ч, узлов в сети и соседей напрямую, заблокировано пакетов; диагностика — аптайм, сигнал Wi-Fi, свободная память, причина перезагрузки. Тяжёлые графики и история — в HA, не на плате.

## Канал «Дом»: чат с Home Assistant через mesh

Приватный канал MeshCore, который ретранслятор передаёт в HA и обратно. В приложении это обычный групповой чат.

1. В приложении MeshCore создайте приватный канал (например, «Дом») и скопируйте его ключ (поделиться → ключ / QR).
2. На ретрансляторе (USB, веб-консоль или «Настройки → Канал «Дом»»): `home channel <ключ>` — hex или base64, как даёт приложение. Ключ хранится в NVS и нигде не выводится; через LoRa команда недоступна.
3. Проверка: `home say проверка` — сообщение появится в канале в приложении.

Дальше (нужен MQTT, см. выше):
- сообщение из канала → тема `senkophone/<id>/chat/in`: `{"from":"Ivan","text":"свет кухня вкл","snr":7.25,"hops":1}`;
- текст в `senkophone/<id>/chat/out` (просто текст или `{"text":"..."}`, до ~600 байт) → ретранслятор пишет его в канал от своего имени; длинный текст он сам делит на пакеты `… [1/3]`, `… [2/3]` (по строкам и пробелам, не разрывая символы) и отправляет их с паузой 12 с, чтобы не перепутался порядок;
- в HA появляются «Канал Дом: сообщение» (последнее сообщение, атрибуты from/text/snr/hops) и поле «Канал Дом: отправить».

⚠️ Подлинность в канале держится только на ключе: имя отправителя внутри сообщения не защищено, любой, у кого есть ключ, может написать что угодно. Поэтому в автоматизациях HA — только заранее заданные фразы и безопасные действия; при утечке ключа — новый ключ в приложении и `home channel <новый>`. Сообщения канала идут по сети флудом (пересылаются всеми репитерами, но без ключа не читаются).

Пример автоматизации HA (белый список фраз и ответ в канал):

```yaml
alias: Mesh — канал Дом
mode: queued
triggers:
  - trigger: mqtt
    topic: senkophone/<id>/chat/in
actions:
  - variables:
      cmd: "{{ trigger.payload_json.text | lower | trim }}"
  - choose:
      - conditions: "{{ cmd == 'свет кухня вкл' }}"
        sequence:
          - action: light.turn_on
            target: { entity_id: light.kuhnia }
          - action: mqtt.publish
            data: { topic: senkophone/<id>/chat/out, payload: "свет на кухне включён" }
      - conditions: "{{ cmd == 'статус' }}"
        sequence:
          - action: mqtt.publish
            data:
              topic: senkophone/<id>/chat/out
              payload: "дома {{ states('sensor.temperatura_zal') }}°C"
    default:
      - action: mqtt.publish
        data: { topic: senkophone/<id>/chat/out, payload: "не понял: {{ cmd }}" }
```

## Наблюдение за узлами

Список до 8 узлов (ключевые репитеры сети), которые должны быть слышны. Если узел не слышно — ни напрямую, ни в путях чужих пакетов — дольше порога, в канал «Дом» уходит «⚠ Узел … молчит больше N ч», а в Home Assistant бинарный датчик «Узел …: на связи» становится «нет связи»; когда узел снова слышен — «✅ … снова на связи». После перезагрузки платы отсчёт идёт с момента запуска.

CLI: `watch`, `watch add <ID hex> [часы]` (по умолчанию 6, 1–168), `watch del <ID hex>`. В панели — «Сеть → Наблюдение за узлами» и глаз 👁 в таблице соседей. ID — первые байты ключа узла (как в таблице соседей), например `4869`.

## Чат в панели

Вкладка «Чат»: последние 30 сообщений канала «Дом» (входящие, ответы HA, тревоги наблюдения) и отправка от имени ретранслятора. История — в памяти платы, с момента загрузки.

## Автообновление

Плата сама проверяет выпуски: через 5 минут после включения и раз в сутки читает `manifest.json` (и `manifest.sig` рядом с ним) по адресу из настроек.

- **Принимается только подписанный выпуск.** Подпись Ed25519 проверяется открытым ключом, вшитым в прошивку (`DIY_UPDATE_PUBKEY` в `variants/diy_e22_wroom32/platformio.ini`). Закрытый ключ есть только у CI. Сертификаты TLS не проверяются: подлинность даёт подпись.
- **Проверки:** плата в манифесте = своя (`e22wroom`), версия новее текущей, бета — только если разрешено.
- **Установка** идёт в отдельной задаче, радио работает. SHA-256 файла считается по ходу записи во второй слот; не совпал — слот не переключается.
- **Самооткат:** если новая версия перезагрузится больше 3 раз, не проработав 10 минут, плата вернётся на прежний слот.
- **Режимы:** `off`, `notify` (по умолчанию: сообщать в панели и на экране), `auto` (ставить ночью, 00–03 UTC = 03–06 МСК; dev-сборки не трогает).

CLI: `update`, `update check`, `update install`, `update mode off|notify|auto`, `update beta on|off`, `update url <адрес manifest.json>`. В панели — «Обслуживание → Автообновление».

### Ключ подписи (один раз)

```bash
openssl genpkey -algorithm ed25519 -out senkophone-update.pem
openssl pkey -in senkophone-update.pem -pubout -outform DER | tail -c 32 | od -An -tx1 -v | tr -d ' 
'
```
- Вторая команда печатает открытый ключ (64 hex) — он идёт в `DIY_UPDATE_PUBKEY`, это не секрет.
- Содержимое `senkophone-update.pem` — секрет Forgejo Actions `UPDATE_SIGNING_KEY`; копия — в менеджере паролей; файл после этого удалить.
- Переменная Forgejo `UPDATE_URL_BASE` — откуда плата качает файлы, например `https://github.com/OWNER/REPO/releases/download`.
- Без секрета или переменной CI только предупреждает, и выпуск платам не предлагается.

При выпуске CI делает `manifest.json` (`diy/scripts/make_manifest.py`) и `manifest.sig` и прикладывает их к выпуску.

## Публикация на GitHub (SenkoOS)

Публичная копия — https://github.com/Geraltrot/SenkoOS. Это не зеркало рабочей истории: при каждом выпуске CI (`diy/scripts/publish_github.sh`) делает там **один коммит** с деревом этого выпуска поверх предыдущего, тег и GitHub Release с `<тег>.bin`, `<тег>-merged.bin`, `manifest.json`, `manifest.sig`. Платы берут обновления с `…/releases/latest/download/manifest.json` (последний обычный выпуск, без бета).

Перед отправкой всё дерево и текст выпуска проверяются по `PRIVACY_PATTERNS`; при совпадении ничего не публикуется. Без переменной `PRIVACY_PATTERNS` публикация запрещена.

Нужно в Forgejo (Настройки → Действия): секрет `GH_TOKEN` — fine-grained токен GitHub с доступом только к этому репозиторию и правом Contents: Read and write; переменные `GH_REPO` (`Geraltrot/SenkoOS`) и `UPDATE_URL_BASE` (`https://github.com/Geraltrot/SenkoOS/releases/download`). В репозитории GitHub выключены Actions (workflow от upstream там не нужны, сборка — только в Forgejo). Без секрета шаг лишь предупреждает.

## Язык панели

Панель на русском и английском: кнопка `EN` / `RU` в шапке (и ссылка на странице входа), выбор запоминается в браузере; по умолчанию — язык браузера. Страница пишется по-русски, перевод — словарь фраз `diy/firmware/web/i18n_en.js`, который при сборке встраивается в страницу (`embed_web.py`); при английском всё, что появляется на экране, проходит через него. Сообщения канала и вывод консоли не переводятся. Новый текст в панели — добавить фразу в словарь; проверка: открыть `index.html` с диска в браузере с английским языком.

## Что изменено относительно upstream

- `variants/diy_e22_wroom32/`: вариант платы (platformio.ini, target.h, target.cpp).
- `diy/firmware/`: своё приложение. `main.cpp` повторяет upstream `simple_repeater/main.cpp` и добавляет `DiyMesh` (наблюдение и фильтры поверх `MyMesh`), Wi-Fi (`WifiLink`), NTP и веб-панель (`WebPanel`, `JsonOut`). `MyMesh` и `UITask` берутся из upstream без правок.
- `diy/scripts/`: скрипты сборки.
- `diy/`: этот README и список доработок.

Файлы upstream не изменены.

## Ветки

- `main`: проверенные версии, которые прошиваются на устройство.
- `dev`: текущая работа. В `main` попадает только через MR после зелёной сборки CI.
- `upstream`: remote оригинального MeshCore, оттуда забираются новые релизы.
